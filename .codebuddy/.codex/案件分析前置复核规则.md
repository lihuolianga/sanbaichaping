# 案件分析前置复核规则

每次分析“新的案件”之前，必须重新核对当前工作区，不得直接沿用历史报告、旧记忆或旧规划文件中的章节边界。

| 不要 | 必须做 |
|---|---|
| 直接相信上次记录的“正文到第X章” | 用 `rg --files` 或等价方式重新枚举各卷正文文件 |
| 只检查已跟踪文件 | 同时检查未跟踪文件和 `git status --short` |
| 由卷纲决定“新的案件” | 先找当前最高正式正文，阅读末章实际钩子，再对照卷纲 |
| 把旧 `findings.md` 当现状 | 把旧记录视为历史数据，发现冲突时以当前物理文件和正文为准 |
| 看到第316章旧报告就停止 | 检查第317章及以后是否存在，再确定真正的新案件 |
| 把计划或提示词说成已执行正文 | 分开报告已写正文、卷纲计划和未写章节 |

最低检查项：

1. 当前正式正文最高章节号。
2. 最高章节号对应的真实文件路径。
3. 是否存在未跟踪的新章节。
4. 最高章节末尾实际引出的案件。
5. 该案件的正文文件是否已经存在。
6. 与卷纲中的案件编号是否一致。

## 提示词落地规则

- 新案件分析完成后，完整 CodeBuddy 提示词必须直接写入项目根目录的 `案件提示词` 文件夹。
- 文件名统一使用：`案件{编号}_{案件名称}_完整提示词.md`。
- 聊天回复只需给出案件结论、文件链接和必要摘要；不得只在聊天中输出提示词而不落盘。
- 提示词文件必须包含：事实边界、读取文件、案件机制、逐章任务、写作禁区、允许修改范围和完成后验收标准。
- `优化提示词` 文件夹用于优化既有提示词，不作为新案件提示词的默认落点。
